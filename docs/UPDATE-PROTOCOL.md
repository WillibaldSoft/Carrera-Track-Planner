# Standalone update protocol, format 1

Checks use the fixed public `WillibaldSoft/Carrera-Track-Planner` repository and the newest stable release. No release-supplied URL outside that repository's expected download prefix is accepted. Prereleases, drafts and downgrades are excluded. The [GitHub Releases API](https://docs.github.com/en/rest/releases/releases) exposes uploaded asset digests; [GitHub documents SHA-256 asset digests](https://github.blog/changelog/2025-06-03-releases-now-expose-digests-for-release-assets/).

`Carrera-Track-Planner-update.json` has `kind: carrera-planner.update`, `format: 1`, a stable `version`, `minimumNode`, and a `files` map. Every path maps to canonical base64 `data` and hexadecimal `sha256`. The complete downloaded asset must match both its GitHub digest and the single matching SHA256SUMS row. The package's `dist/release.json` must identify the same version and application.

Allowed application entries are `dist/`, `updater/`, `LICENSES/`, launcher, standalone server, README, LICENSE, NOTICE, SOURCE.txt and third-party notices. Runtime binaries, arbitrary paths, traversal, Windows reserved paths, duplicate/case-conflicting paths, symlinks and files outside this allow-list are rejected. Limits apply to downloads, file count and total decoded size. Every `.mjs` is syntax-checked by the existing Node runtime before replacing files. Format 1 must retain backwards-compatible saved-plan storage; it is not a runtime or data-migration protocol.

The standalone server is loopback-only. Host validation, same-origin/Fetch Metadata checks, JSON requests, a session confirmation token and an already checked matching version guard installation. The release is rechecked before downloading. New writes are blocked during installation, after prior store writes finish. A per-application filesystem lock prevents simultaneous installers. Startup settings only authorize metadata checks, never installation.

Files are staged inside the application directory. A separate per-user backup preserves application files and the saved-plan file. Backup hashes are verified before modifying the application and again before restoration. Runtime, installation-mode marker and current user data are never replaced by the update payload.

A preserved supervisor starts from the old backup, waits for the old process to exit, launches the new application and checks both version and PID via loopback health checks. A startup timeout restores the verified old application and validates its restart. Application rollback never rolls back newer user plans. Interrupted updates and recovery failures are reported rather than silently retried. Backups are retained for manual recovery; see the language-specific guides.

`update-installation.json` marks packaged portable or managed per-user deployments. Debian system installations keep their package-manager workflow. Source checkouts, read-only deployments and unsupported platforms expose manual instructions. Embedded mode uses `/api/addons/track-planner/updates/{info,check,install}` when provided by the local host extension and never calls the standalone installation API. The host validates the official add-on asset and individual files, snapshots program files and the database, then runs its existing regression gate. Failed checks restore program files and the previous host build/approval without restoring older user data. Installation requires a same-origin, loopback request and a session confirmation token. Hosts without this capability retain manual download. Windows artifacts are packaged; native Windows execution remains unverified in the Linux build environment.
